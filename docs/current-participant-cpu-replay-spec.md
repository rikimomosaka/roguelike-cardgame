# 参加者別戦闘・CPU味方・行動再生 現行仕様

この文書は、味方召喚をカードで行動するCPU参加者へ移行し、将来の協力
マルチプレイと共通化するための現行仕様である。既存のソロ戦闘と競合する
記述がある場合、この文書を優先する。

## 1. 参加者と戦場

- `CombatActor` はHP、ブロック、状態変化、予約攻撃など戦場上の身体を持つ。
- `BattleParticipantState` は操作主体ごとのカード資源を持つ。
- 人間とCPUは同じ参加者モデルとCoreコマンドを使用する。
- 各参加者は山札、手札、捨札、除外、パワー、召喚保持、エナジー、
  コンボ、最大コンボ、ワイルド状態、コンボゲージ、使用回数、選択待ち、
  対象選択、Readyを独立して所有する。
- 同一カードIDのターン使用回数は同じ参加者内で共有し、別参加者とは共有しない。
- CPU味方にも特性、戦技、奥義、レリック、ポーションを設定できる。ただし
  初期ウィスプでは使用しない。
- ドロー、エナジー、ターン開始時エナジー追加量、カードコスト変更は、
  `self` のほか `single/random/all + ally` で別参加者を対象にできる。
  対象参加者自身の手札上限・混乱・カード領域へ適用し、過去の確定行動には
  遡及しない。管理画面と自動説明も同じ対象指定を使用する。
- `deck` を持つ敵はカード制御（`current-enemy-card-ai-spec.md`）。敵のカード資源は
  `BattleState.EnemyParticipants` に分離し、本節の参加者・Ready 同期には含めない。
  `deck` の無い敵は移行完了まで固定Move方式。

## 2. 召喚

- 味方召喚に寿命ターンの概念を使用しない。
- 召喚はHPが0になる、明示的に退場する、または戦闘が終了するまで残る。
- 召喚時に専用デッキと参加者状態を新規生成する。同種の別個体とも共有しない。
- 召喚カードは従来どおり召喚者の召喚保持領域へ移動し、召喚死亡時に
  その召喚者の捨札へ戻す。
- Unitカード自身の`召喚`効果が生成したactor IDだけを、そのUnitカードと
  明示的に関連付ける。`OnPlayCard`のレリック／パワーが後から生成したactorは
  その関連付けに含めない。
- 1枚のUnitカードが複数体を直接召喚した場合、全員を1つの所有グループとする。
  カードは召喚保持に1枚だけ置き、グループ最後の1体が退場した時にだけ捨札へ戻す。
- 召喚直後は初期エナジーと初期手札を受け取り、通常のターン開始時状態効果は
  次ターンから処理する。
- CPU召喚は生成したコマンドの処理内で直ちに全行動を決定し、Readyになる。
- CPUが別CPUを召喚した場合、現在のカード解決後、生成順に処理する。

### 初期ウィスプ

- HP: 30
- 初期エナジー: 1
- ターン開始時エナジー追加量: 1
- ドロー: 3
- 手札上限: 5
- 未使用エナジーは持ち越す。
- デッキ:
  - 鬼火（0コスト、敵単体に1アタック）x2
  - 火花（1コスト、敵単体に3アタック）x2
  - 燐盾（1コスト、自身に3ブロック）x1
  - 散火（2コスト、敵全体に2アタック）x1

## 3. PlanningとReady

- 味方全員が行動を決める期間をPlanningとする。
- ターン終了ボタンはReadyの切り替えである。
- Ready後、解決開始前なら再度押して解除できる。過去の行動は巻き戻さない。
- 生存中かつ行動参加資格のある全参加者がReadyになったコマンド内で、状態を
  原子的にResolvingへ移す。
- Resolving開始後はReady解除、カード、選択、戦技、奥義、ポーション、対象変更を
  禁止する。
- 同時コマンドはルーム単位の直列順とrevisionで確定する。
- CPUはターン開始処理完了後、Slot順で人間より先に全行動を決めReadyになる。
- ターン開始時は全参加者のエナジー追加・手札更新を先に完了してから、
  各参加者が所有するターン開始時レリック・パワーをSlot順で処理する。
- CPU処理中に別コマンドを割り込ませない。

### Ready後の新しい行動機会

- 他参加者の効果により合法な行動が新たに増えた場合、過去の行動を変えずに
  Readyだけを解除する。
- CPUは追加分を即時判断して行動し、再びReadyになる。
- 人間はReady解除と再行動可能の通知を受ける。
- 筋力など最終予定値だけを変える効果、または合法な行動を減らすだけの効果では
  Readyを解除しない。
- 「新たな合法行動」はカード、戦技、奥義、ポーション、選択解決の合法集合を
  効果の前後で比較して判定する。

## 4. CPU判断

- CPUはカードを1枚使うたびに合法候補を再計算する。
- 候補比較順:
  1. コンボ軽減を受けてコンボが継続する。
  2. 軽減はないがコンボが継続する。
  3. コンボが途切れる。
  4. 実支払コストが低い。
  5. Unit固有priorityが高い。
  6. 手札の左側にある。
- コンボ0の最初の1枚はコンボ継続として扱わない。
- 使用可能な行動がなくなるまで続け、エナジーは意図的に温存しない。
- 1キャラ30行動、CPU全体100行動を1ターンの安全上限とし、同一状態再訪も停止する。
- 単体攻撃対象は「そのカードで倒せる敵、HPが少ない敵、Slotが小さい敵」の順。
- AI判断理由は開発時だけ記録・表示し、本番DTOへ公開しない。
- 現行 `low_cost_combo` profile の自動選択対象はカードである。Unitには共通形式の
  戦技・奥義・レリック・ポーションを設定でき、共通Coreコマンドでも使用できるが、
  CPUがそれらを選ぶ優先規則は初期ウィスプでは未使用のため今後のprofile拡張とする。

## 5. 行動決定と最終解決

戦闘情報を次の3層へ分離する。

1. `CommittedAction`: 使用カード、支払、対象、選択、使用回数など確定済みの過去。
2. `Intent`: 全員Ready後に解決する攻撃・ブロック等の予約。
3. Live state: 現在のHP、状態変化、資源、カード領域、Ready。

後からエナジー、ドロー、コスト変更、使用制限を受けても、支払済みコスト、
過去の合法判定、カード移動、使用回数、コンボ結果を変更・取消・返金しない。
未使用のカードと以後のコマンドだけに適用する。

Intentへ使用時に固定するもの:

- 基礎攻撃値・基礎ブロック値
- AmountSourceの使用時算出値
- ヒット数
- 宣言時の攻撃範囲
- 選択対象
- 発生源、Action ID、順序

解決時のLive stateから参照するもの:

- 筋力、脱力、元気、敏捷、脆弱
- 拡散（有効なら予約済み攻撃も全体化し、失えば宣言範囲へ戻る）
- 追撃、バリア、反射、吸血などの戦闘反応
- 攻撃者・対象の生死

先行参加者によって対象が攻撃開始前に死亡していた場合、対象方針で再選択する。
同じ参加者の一連の攻撃中に対象が死亡した場合、その対象へ予約された残りの
単体攻撃は不発とする。Randomは各ヒットの生存対象から選び、Allは生存者全体へ
適用する。

Resolving中に発生した効果は既存ソロと同じ順序で処理し、Planningを再開しない。

## 6. 行動ログと再生

- 全コマンドをBattleRevisionと単調増加sequenceの順で記録する。
- 行動ログは戦闘を再実行する入力ではなく、確定済み結果の表示記録である。
- 各ActionはParticipant、Actor、カード表示snapshot、支払、対象、選択、即時イベント、
  生成Intent、Ready変化、前後revisionを持つ。
- 別参加者から受けた影響も、対象参加者の再生へ時系列順で外部効果として挿入する。
- 発生元参加者の再生では元カード・能力を通常表示し、対象側ではコンパクトに
  「誰の何により何が変化したか」を表示する。
- 決定時ログは後から書き換えない。頭上の現在予定はLive stateで更新する。
- 全員Ready後の実ダメージ等は共有の最終解決ログとして再生する。

### 再生UI

- 遷移ボタンは各味方のHP下、キャラ名の右側。
- 再生操作は画面中央のコンボ・戦技・奥義の上にまとめる。
- `戻る`、`最初から再生`、進行数、`LIVE/READY`、速度、スキップを表示する。
- 未Ready人間の新規ログは開いている再生の末尾へリアルタイム追加する。
- 再生中は専用presentation stateを使い、最新live stateと混ぜない。
- 各ログは全actor・全participantを含む完全な前後presentation snapshotを持つ。
  後で死亡・退場した対象も、その時点の再生では当時の状態で表示する。
- カード行動は共通カードの中央表示、攻撃移動、被弾表示をpresentation-onlyで
  再生してからafter snapshotへ進める。再生はCoreを再実行せずlive stateを変更しない。
- 再生完了後も自動では戻らず、途中でも`戻る`で最新live stateへ復帰できる。
- 全員Readyになった場合、再生中の1行動を終えた後、共有解決演出へ移る。

## 7. 将来のマルチプレイ移行境界（未実装）

現段階で完成しているのは、1戦闘内の参加者別状態・CPU操作・Ready同期・
行動ログ／再生というソロ協力の基盤である。複数accountが同じ戦闘へ接続する
実マルチプレイはまだ完成扱いにしない。以下は実マルチプレイ開始前に必須となる
P0契約であり、現行のaccount単位BattleSession/lockをそのまま流用してはならない。

- コマンドはParticipant ID、Actor instance ID、Card instance ID、Command ID、
  expected revisionを受け取る構造にする。
- ServerはaccountがParticipantを操作できるか検証する。
- 戦闘更新はaccount単位でなくroom/battle単位に直列化する。
- battle/room IDから共有state・RNG・journalを一意に解決し、accountからは
  所有Participantだけを操作できるようにする。
- 接続・切断・再接続と最新stateの配信は、room単位のSignalR同期として別途実装する。
- CPUも人間も同じCoreコマンドを使い、専用の効果適用近道を作らない。
- 切断時CPU代行は同じCPU判断器と行動ログを再利用できるようにする。
