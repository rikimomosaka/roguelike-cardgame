# コンテンツ・ワークベンチ現行仕様

更新日: 2026-08-15

## 目的

ゲームのマスターデータをブラウザ上で一覧・編集・検証し、Development環境の実ゲームへ安全に反映する。既存のカード専用／レリック専用画面は入口を統合し、未知のJSONフィールドを失わない共通ワークベンチへ置き換える。

## 開き方

ServerとClientを起動し、`http://localhost:5173/?dev=cards` を開く。`?dev=relics`、`?dev=events` などを指定した場合も同じワークベンチの該当カテゴリを開く。

管理画面だけはゲーム本体の1280×720固定拡大を使わず、ブラウザの表示領域全体を使用する。Production環境では開発APIを公開しない。ブラウザE2E環境は一覧とプレビューだけを読み取り専用で公開し、リポジトリ上のoverrideを変更できない。

「構造化編集」は配列の追加・削除・並べ替え、真偽値／数値／文字列の編集に対応する。効果、対象範囲、対象陣営、発火条件、ステータス、イベント効果、イベント条件、マス種別、カード・敵・召喚・レリック参照など、閉じた候補は選択式にする。任意辞書や将来追加された未知フィールドはJSON編集でも変更できる。

### 編集画面の補足

- `変更あり` は、組み込みの標準データへ開発用overrideを重ねている状態を表す。標準ファイル自体は変更せず、実ゲームは両者を合成して利用する。「変更を破棄」で標準状態へ戻る。標準を持たない項目は管理画面で追加した新規データである。
- `未設定（null）` は、その任意項目に値が設定されていないことを表す。設定するときだけ「文字」「数字」「ON/OFF」「一覧」「詳細項目」から入力形式を選ぶ。未設定のままでよい項目は操作しない。
- 選択肢は保存されるIDと日本語名を必ず `id(名前)` で併記する。例: `buff(バフ)`、`strength(筋力)`。保存されるのは従来どおりIDだけであり、日本語名を変更しても既存データは壊れない。
- カードの各versionの`spec`に`upgradedEffects`が無い場合は、「通常効果を複製して強化後を作成」を押す。通常効果のコピーが強化後欄として作られ、その値や項目を編集できる。既に`upgradedEffects`がある場合は、その配列内の「項目を追加」で強化後の効果を増やす。
- カードの通常版と強化版のキーワードは独立している。対象versionの`spec`で「通常版キーワード欄を追加」「強化後キーワード欄を追加」をそれぞれ使い、別々に選ぶ。強化後へ通常版を自動継承・自動コピーしない。空配列は「その版にはキーワードなし」を明示する。
- `usesPerTurn`（通常版）と`upgradedUsesPerTurn`（強化版）はカード本体の1ターン使用回数で、互いに独立している。ポーションとキャラクタースキルも各データ本体の`usesPerTurn`へ設定する。個々のeffectへ`usesPerTurn`を置くことは禁止し、保存前検証でエラーにする。
- 同じ対象へ複数のバフまたは複数のデバフを付与する場合、効果編集欄の
  「状態を追加」で1個の`statusChanges`へまとめる。バフとデバフは別効果にする。
- 即時ドローを持つアタック／スキルカードは通常版・強化版それぞれ
  `usesPerTurn: 1`を必須とする。パワーと、洞察など発動時点が固定された間接ドローは対象外。
- バリアまたは復活を付与するアタック／スキルカードは、通常版・強化版それぞれ
  `exhaust`（喪失）を必須とする。
- effectの`action`を変更すると、そのactionで必要になる対象範囲、対象側、ステータス、参照カード、召喚ID、対象領域、選択方式などを一式生成する。例として`debuff`ではデバフ種別だけを選べるステータス欄を必ず表示する。変更前actionだけで使う既知項目は除去するが、未知の将来拡張項目は保持する。
- `draw` / `drawCards` / `gainEnergy` / `gainMaxEnergy` / `modifyCardCost` は、`self`または`single/random/all + ally`を選べる。非self時は敵側を選べず、自動翻訳にも「味方単体」「ランダムな味方」「味方全体」を表示する。`modifyCardCost`の手動選択（`select: choose`）だけは操作主体自身に限定する。
- versionedデータは`activeVersion`だけを最初から展開し、それ以外のversionは折りたたむ。各versionの見出しから個別に開閉でき、使用中versionは金色の「使用中」表示で識別する。「バージョンを追加」は、既存versionがあれば使用中specを複製して次の`vN`を採番する。初回versionでは、カードはレアリティ・種別・コスト・通常／強化効果・通常／強化キーワードを、レリックはレアリティ・説明・効果・実装状態を備えた編集可能な雛形を作る。
- JSONに存在しない任意項目は「追加できる既知の設定」から選ぶ。現行loaderが認識する任意項目はここから追加できる。「高度なJSON項目を手動追加」は、まだUIが知らない将来の拡張項目や、開発途中の独自プロパティを試すための退避口であり、通常の既存データ編集では使わない。
- ゲーム表示プレビューは入力後250msでCoreの自動翻訳を再実行する。`[N:...]`、`[S:...]`、`[K:...]`などは保存用の内部マーカーで、プレビューではゲーム本体と同じリッチテキストへ展開する。ステータスとキーワードはマウスホバーまたはキーボードフォーカスで、ゲーム共通定義の名称・説明ツールチップを表示する。

## 保存と安全性

1. UIは読み込んだ完全なJSONを保持し、認識していないフィールドも往復で残す。
2. 保存前に、対象変更を全コンテンツへ仮適用した候補カタログを構築する。
3. 各loaderの構文検証に加え、カード参照、召喚ID、ステータスID、敵／召喚行動の遷移先などを横断検証する。
4. 検証成功後だけ、固有名の一時ファイルから `data-local/dev-overrides/<分類>/<id>.json` へ原子的に置換する。
5. runtime catalogは完全な新snapshotが完成してから一度に交換する。以後に開始するrunは新snapshotを使う。
6. revisionが読み込み時から変わっていた場合は409で拒否し、別画面の変更を無言で上書きしない。
7. baseとoverrideの両方がある項目はoverrideだけを破棄してbaseへ戻せる。新規項目は既存項目の複製から作成できる。
8. カード／レリックの「決定稿を標準v1へ」は、現在のフォームにある使用中specだけを`v1`へ正規化し、標準JSONへ原子的に保存する。既存標準ファイルは`data-local/backups/<分類>/`へ退避し、成功後にoverrideを削除する。実行中Serverでは再buildまでの間も同じ決定稿をauthoring snapshotとして保持する。

ブラウザには未保存表示、離脱警告、40段階のUndo/Redo、検証のみ実行、参照元一覧がある。検証・保存などの結果通知は開いているデータだけに属し、別のデータや分類へ移動した時点で消去する。

## 共通化した契約

- カード、ポーション、レリック、固有スキル、敵行動、召喚行動はCoreの `CardEffect` と `CardTextFormatter` を共用する。使用回数制限はeffectではなく、実際に使用するカード・ポーション・固有スキル本体へ置く。
- effect action、trigger、amount source、イベント効果／条件の語彙はCoreの `ContentAuthoringCatalog` を正とし、旧エディタと新ワークベンチの両方へ同じ一覧を配信する。
- 状態変化候補はCoreの `StatusDefinition.All`、キーワード候補は `CardKeywords.All` を直接使用する。
- カード／レリックのversioned JSONは既存mergerを使用する。完全な新規overrideも同じruntime catalogへ追加できる。
- 非versionedデータはID単位の完全置換とし、カード／レリックだけは既存の部分overrideとの互換性を維持する。

## 意図的に未実装の範囲

以下は単なるJSON追加では実行時の意味を定義できず、Core/Udon#互換ルールを伴うため、今回の初期版では読み取り専用または汎用表示に留める。

- 新しい状態変化の新規作成（減衰時機、重複、符号、ダメージ処理などの実行規則が必要）
- 新しいeffect actionの新規作成（resolver、対象選択、イベント、翻訳、決定性テストが必要）
- 画像のアップロード、透過検査、ドット絵スプライト分割
- イベント／マップ／報酬のゲーム画面そのものを再現する専用ビジュアルプレビュー
- 公開用version履歴、複数変更をまとめたリリース単位のcommit/rollback

## 次段階

1. 状態変化を「表示メタデータ」と「既知の実行policy ID」に分離し、安全なpolicyの範囲でデータ作成可能にする。
2. effect actionの入力schemaをCoreのauthoring metadataへ移し、Client内の入力schemaも含めた完全な単一情報源にする。
3. 画像ライブラリ、PNG寸法／透過／pixel-art承認manifest、スプライトプレビューを統合する。
4. 複数項目を作業セットとして保存し、一括検証後にpublish／rollbackできるようにする。
5. 参照グラフを専用indexへし、データ増加時も一覧取得を一定時間に保つ。
