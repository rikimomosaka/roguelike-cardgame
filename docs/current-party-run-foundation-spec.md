# パーティラン基盤・キャラクターピック仕様

最終更新: 2026-08-20

この文書は、キャラクターピックと将来の最大4人パーティに向けた、現在の保存・開始処理の実装境界を定義する。

## 1. 現在実装する範囲

- ラン開始前にキャラクターを選択する。
- 現段階で実際に開始できるランは1人プレイとする。
- Coreの保存形式は1～4人のパーティを表現できる。
- 2～4人を指定した開始要求は、戦闘開始・終了の複数人対応が完成するまで明示的に拒否する。先頭の1人だけで開始する縮退処理は行わない。
- 既存のbodyなしラン開始は、従来どおり `default` キャラクターを選んだものとして扱う。

## 2. 保存モデル

ラン保存schemaはv8とする。

`RunState.PartyMembers` は、各プレイアブルキャラクターが個別に所有する次の状態を保持する。

- キャラクターIDとパーティスロット
- 現在HP、最大HP
- ゴールド
- デッキ
- レリック
- ポーションと所持枠
- 報酬、商店、イベント、休息、幕開始レリック選択の個別状態
- カード・レリック・ポーションの取得履歴
- 戦闘外の操作担当（人間またはCPU）

マップ、現在ノード、遭遇、戦闘、進行状態、Journey、基幹RNGはパーティ共有とする。

既存処理との互換期間中は、`RunState` 直下の単一キャラクター用フィールドをホストメンバーのミラーとして残す。`RunPartyAccess` が次を担う。

- 旧形式の状態をホストメンバーへ初期化する。
- ホストの直下状態をパーティ状態へ取り込む。
- 任意メンバーを既存の単一キャラクター処理へ投影する。
- 処理後の結果を対象メンバーへ戻し、直下にはホストを復元する。

## 3. 互換性

- v7保存は、既存の所有データを `player:0` へ移してv8へ変換する。
- `player:0` をホストとする。
- 既存の単一キャラクター用API・画面には、ホストの互換値を返す。
- 保存前とDTO投影前に、直下の最新状態をホストメンバーへ同期する。

## 4. キャラクター選択契約

ラン開始要求は次の形を使用する。

```json
{
  "characterIds": ["default"]
}
```

- 将来契約として1～4件を表現する。
- キャラクターID、メンバーID、パーティスロットは重複不可。
- 配列順をパーティスロット順とする。
- 未知ID、空文字、0件、5件以上は不正とする。
- bodyなし、`{}`、`characterIds: null` は既存互換として `default` 1人を選ぶ。
- 現段階では2～4人の正しい要求にも「パーティ戦闘未接続」を返し、壊れたランを生成しない。

ピック画面は4クラス（ストライカー、ガーディアン、タクティシャン、エンハンサー）を表示し、カタログのキャラクターを動的に列挙する。キャラクター名、クラス、HP、説明、特性、初期デッキを確認して開始できるようにする。

## 5. 確定済みの将来仕様

- 最大4人のプレイアブルキャラクターを選択できる。同一キャラクターの重複選択は禁止し、同一クラスの別キャラクターは選択可能。
- ゴールド、HP、デッキ、レリック、ポーション、報酬、商店、休息、イベント選択は各メンバーで独立する。
- マップ進行と戦闘は共有する。
- ソロで複数人を選んだ場合、CPU戦闘と手動戦闘外管理を併用し、画面上で操作対象を切り替える。
- プレイアブルキャラクターはターン中にも手動・CPUを切替可能。ただし確定済みの行動は巻き戻さず、次のターンから反映する。
- メイト（召喚キャラクター）はCPU固定。
- CPU行動順は `S1 → S2 → S3 → P1 → P2 → P3 → P4` とする。メイト側・後衛側が先に支援し、前衛が後から行動する。
- 人間所有のプレイアブルキャラクターが全滅した時に敗北する。CPU所有キャラクターやメイトだけが残っても継続しない。
- プレイアブルキャラクターは最大4枠、メイトは常に共有3枠とする。人数が少なくてもメイト枠は増えない。
- 敵スケーリングは編成数を増やすより、主にHP・ブロックと、人数によるバフ／デバフ相乗効果を考慮した非線形補正で行う。

## 6. 次の実装段階

1. `BattleEngine.Start` が全パーティメンバーからactor・participantを生成する。
2. `BattleEngine.Finalize` が各participantを対応するメンバーへ個別保存する。
3. プレイアブル4枠とメイト3枠を、役割とformation slotで明示的に分離する。
4. 報酬、商店、休息、イベントをメンバーID指定で投影・確定する。
5. キャラクター操作担当の切替を、次ターン適用の予約状態として実装する。
6. 人数別の敵HP・ブロックスケーリングをデータ化する。
7. その後、ルーム共有、参加者認証、再接続、SignalR配信を実装する。

実ネットワークマルチが完成するまでは、複数人ランを「マルチプレイ対応済み」とは扱わない。
